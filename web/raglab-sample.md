# 大大怪多智能体助手技术说明

大大怪技术白皮书 · 内部资料 v1.2

## 一、系统概览

大大怪是一个跑在单台 Windows 工作站上的多智能体系统，面向 QQ 群聊、私聊与网页端，同时提供文生图、角色扮演、长篇小说和漫画生成四类能力。整套系统没有使用任何云函数或容器编排，所有服务以常驻进程的方式运行在本机，通过本地端口和反向代理对外暴露。

系统分为四层。第一层是接入层，包括 QQ 机器人进程、独立的小程序网关和网页前端；第二层是编排层，负责判断用户意图、选择渠道、组织提示词；第三层是模型层，包括本地 ComfyUI 推理服务、本地小向量模型和多个云端大模型；第四层是数据层，保存会话状态、向量库、图片产出和运行日志。

这样的分层带来一个直接好处：每一层都可以单独替换。换一个云端模型只影响编排层的候选链，换一个生图渠道只影响模型层的渠道登记，不需要改动上层业务代码。代价是进程数量较多，需要一套统一的启动和监控方式。

本机常驻进程包括：主服务 5174，承载管理页、跑图台、全部 HTTP 接口和 QQ 机器人调用的后端；网关 5175，负责登录、静态页面和反向代理，公网隧道指向它；QQ 机器人进程，独立运行并写自己的日志；ComfyUI 推理服务，监听 8188，由内存守卫看护；向量守护进程，按需要拉起并保持模型常驻。

## 二、生图链路

生图是整个系统里资源消耗最大的部分。一次请求从用户发出一句话开始，依次经过意图识别、渠道选择、提示词翻译、工作流拼装、排队、推理、审核和发送七个环节。

意图识别交给大模型，代码不做事先的关键词匹配。模型判断这一轮要生图后，会给出渠道名和画面描述；如果用户点名了渠道，就直接用点名的那个。渠道清单来自技能目录，每个渠道有一份 ComfyUI 工作流模板，模板里用占位符表示种子、提示词和参考图，运行时替换。

提示词翻译是质量的关键。中文需求先被翻译成英文的画面描述，画面里要出现的文字（招牌、台词、书名）保持原样并用引号写出，其余全部转成英文。角色外观和服饰不交给模型即兴发挥，而是从角色卡里读出固定的英文描述，直接拼进提示词，保证同一个人物在不同轮次里外观一致。

工作流拼装完成后进入队列。系统在两个进程之间共用一把目录锁，同一时刻只允许一张图占用推理服务。这样做的原因是显存只有一张卡，并发提交只会互相触发内存不足。排队期间前端会显示当前排在第几位，等待时间取决于前面有多少张图和它们的步数。

推理完成后还有一道审核。审核只对群聊开启，私聊默认放行。命中敏感判据的图不会直接发出去，而是转到后台等待人工确认，避免误判导致内容外泄。

## 三、角色扮演与长期记忆

角色扮演要解决的核心问题不是文笔，而是记忆。模型本身的上下文窗口有限，一轮对话几千字，聊到三十轮之后早期内容就会被挤出窗口，角色开始忘记之前发生过什么。

系统把记忆分成四层。第一层是短期窗口，保留最近若干轮的原话，保证对话衔接自然；第二层是事实账本，每五轮把这一批对话压缩成不超过一千字的摘要，只保留可以长期复用的事实；第三层是游戏内时间，记录故事进行到第几天、什么时段，影响角色作息和可用场景；第四层是全量归档，所有对话原文按行追加写入文件，只增不删，不进主提示词，用于事后检索和复盘。

在此之上还有一层向量记忆。每一批对话结束后，系统把摘要切分、向量化并入库，同时把原话也按条入库。下一轮开始时，用玩家这句话去检索，命中的条目拼成一段回忆块，注入到最后一条用户消息里。注入时明确标注这只是细节来源，当前这一拍正在发生的事优先，避免角色照着旧对话复述。

向量库按会话线隔离，一条会话线一个集合，集合名是会话标识的哈希。清空存档只删自己那一条线，不影响其他人。向量模型使用本地小模型，五百一十二维，加载耗时在一百毫秒量级，全程占用 CPU，不跟生图抢显存。

检索阈值经过多轮调整。相关记忆的余弦距离一般在零点三四到零点五一之间，闲聊在零点六三以上，因此阈值定在零点六六，配合多样性重排，避免七条回忆全是同一个场景的重复描述。

## 四、小说模式

小说模式与角色扮演共用同一套引擎结构，但目标不同。角色扮演是即时对话，小说模式是长篇叙事，玩家输入的不是一句话，而是一段剧情骨架。

因此小说模式拆成两个模型分工。第一个是编剧，负责把玩家的骨架裁定成结构化的事实，包括地点、在场人物、时间推进、事件状态和持有物变化；裁定不是拒绝，玩家说掏枪但没有枪，编剧会把它变成摸到一根晾衣杆。第二个是写作模型，只负责把这些已经裁定的事实演成正文，不做额外设定，也不替玩家做决定。

世界书是小说模式的数据核心，保存地点、人物、事件、物品和日记。编剧每一轮返回完整的持有物清单而不是增量，数量变化、吃掉、放下、没有带走的长物件都体现在清单里，代码只做归一化，不替模型补状态。这样做的原因是增量更新在长线叙事里几乎必然对不上账。

状态卡从世界书直读，不给数值条。玩家看到的是一张事实卡：现在在哪、身边有谁、身上有什么、还有哪些事情悬着。事件的可见性由地点决定，挂在已经离开的地方的事件不出现在卡上，但数据不删，回到那里还能看到。

回退只保留一步。每一轮覆盖写入一份快照，玩家点回退就恢复这一份，同时清掉当轮写入的向量、恢复输入框里的原话。回退之后必须先再写一轮才能继续回退，避免无限倒退。

## 五、降级链与容错

系统里所有的模型调用都走同一条候选链。链头是调用方点名的模型，后面按配置依次排列备用模型。调用失败时按错误类型决定行为：限流和超时属于可重试，换下一个候选；鉴权失败和余额不足直接拉黑一段时间，避免每轮都去撞墙。

候选链有一个严格模式。严格模式下只打链头，失败就失败，不往后降级。这个模式用在两类场景：一是用户明确选定了某个模型，二是链路隔离要求明确报错而不是悄悄换人。角色扮演和小说模式都使用严格模式的变体，链尾固定为自定义模型和代充付费段，绝不接全局的官方模型，因为官方按量计费，一旦悄悄接管，费用不可控。

生图链路有独立的容错设计。内存不足是最常见的失败原因，系统在提交前检查可用内存，低于水位就重启推理服务再提交。重启有二十秒左右的空窗，这期间提交的图会排队等待。日志里如果看到杀掉进程的字样，要往前看一行，确认是水位触发还是真正的假死。

还有一类失败容易被误判：任务跑完了但没有找到图片。这通常不是真的跑完，而是推理服务执行失败，保存节点没有产出，输出列表为空。判断依据应该看执行状态而不是输出列表，否则会把内存不足报成找不到文件，掩盖真正原因。

## 六、部署与进程拓扑

整套系统部署在一台消费级工作站上，显卡十二吉字节显存，内存十六吉字节。这个配置决定了系统的很多设计：生图必须串行，向量模型必须放 CPU，大模型必须走云端。

进程之间通过 HTTP 和文件目录通信，没有引入消息队列。原因是单机场景下文件锁足够用，引入队列只会增加运维负担。锁的实现是一个目录加上一份心跳文件，持有者定期更新心跳时间，超时未更新视为僵尸锁，可以被抢占。

公网访问通过隧道完成，隧道指向网关端口。网关自己做登录和会话管理，只把接口请求反向代理到主服务。主服务有一道来源校验：来自公网的请求只放行白名单路径，管理页、输出删除和内部聊天接口一律拒绝。这道校验是双保险，防止隧道配置错误时把管理界面暴露出去。

静态资源的分发要特别注意。网关只反代接口路径，页面文件由网关自己读取，所以页面里如果通过相对路径去取额外的脚本或数据文件，在公网访问时会得到四零四。历史上有过这样的问题，解决方式是把这类文件单独加一条路由，或者直接内联进页面。

日志按进程分开写，主服务一份，机器人一份，推理服务一份，看门狗一份。排查问题时先按时间定位，再按进程确认，最后回到代码里找对应分支。只看一份日志往往会得出错误结论。

## 七、常见故障与排查

内存不足是最常见的故障。表现为出图失败、任务莫名消失、推理服务无响应。排查顺序是：先看可用内存，再看推理服务是否活着，最后看显存占用。如果显存被历史模型占满，重启推理服务比反复提交更有效。

模型调用失败是第二类高频问题。表现为回复空白、提示格式错误、提示稍后再试。这里的坑在于错误信息被上层包装过，看起来像是用户输入格式不对，实际是模型接口返回了错误。正确的做法是把接口返回的原始错误记录下来，在后台展示，而不是给用户一句含糊的提示。

向量库问题通常表现为记忆不生效。排查时先确认守护进程是否就绪，再看这一轮有没有触发检索，最后看命中的条数和距离。如果守护进程没就绪，这一轮会静默跳过检索，模型只能从窗口里编，表现为角色记错事。

静态资源四零四是部署问题，不是代码问题。判断方法是本地端口访问正常、公网访问失败，基本可以确定是网关没有转发该路径。

最后一类问题是并发排队。用户看到进度条长时间不动，以为卡死，实际是前面有长任务在跑。区分方法是看锁的持有者和心跳时间，心跳在更新就说明锁是活的，只是队伍长。

## 八、写在最后

这套系统的设计取向可以用一句话概括：把不确定性留在模型里，把确定性写进代码。

凡是需要判断的，交给模型：这一轮要不要生图、这句话是什么意图、这段文字该在哪里断开、玩家这个动作可行不可行。凡是需要核对的，交给代码：这一次调用了哪个模型、花了多少时间、返回了多少字符、向量是多少维、命中了几条。

这样分工的结果是：模型变强，系统整体就变强；模型出错，错误也能被看见而不是被掩盖。对个人项目来说，这比追求一个完美的提示词更可持续。
